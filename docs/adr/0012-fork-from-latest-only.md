# 0012 分叉只从最新处开

- 状态：已采纳（2026-10-30）
- 取代：对话页里「从这里分叉」（逐条消息）和「从某一步分叉…」（填序号）两个入口

## 背景

v1 的分叉让人挑任意一步（atSeq），平台把血缘记得很准，但底层 agent 并不会真的回到那一步：
Pi / Grok / 通用 ACP 都是复用来源会话的完整上下文接着跑。结果是界面写着「从第 3 步分叉」，
agent 却记得第 3 步之后的所有话——标记和实际上下文对不上，比没有这个功能更糟。

调研过 Pi 1.4.0 的 RPC：`get_fork_messages` + `fork {entryId}` 确实能按用户消息切出一份新会话文件，
实测能做到「分叉点之后的话不记得」。但 ACP 系的 agent 没有对应接口，各家语义也不一致；
先不做，留作以后按 agent 能力开放的选项。

## 决定

- 分叉只有一个动作「分叉」（「更多」菜单和 `/fork`），永远从来源会话的最新处开。
- 服务端忽略请求里的 `atSeq`，一律用来源的 `lastSeq`；来源没内容时 409。`atSeq` 字段保留为可选，老客户端不报错。
- 血缘照旧记 `{kind:'fork', fromSessionId, atSeq: lastSeq}`，画布虚线不变。
- 来源这一轮还在跑时，界面上「分叉」置灰并说明原因（此时上下文还没定型）。
- 分叉出来的会话页先显示来源截到 `atSeq` 的对话（只读、变淡），再一条分界线链回来源，然后才是新对话。
  这样「分叉之前说过什么」看得见，不用回来源翻。
- 能力说明改为「只能从最新处分叉：新会话带着来源到此刻的完整上下文，不能挑中间某一步」。

## 后果

- 「标的分叉点」和「agent 实际的上下文」一致了。
- 失去了「从中间某一步重来」；需要时再基于 Pi 的 `fork {entryId}` 按 agent 能力单独开放。
- 已知遗留：Pi 的分叉复用来源的 Pi 会话文件，两边之后的对话都会追加进同一份文件。不在本次范围。
