# ADR 0021：运行时套件（运行时 + 生态组件）

- 状态：accepted（2026-10-31，David 拍板见设计稿 §12，无未决项）
- 日期：2026-10-31
- 关联：ADR 0010、0013、0016、0017、0020；设计稿 `docs/design/runtime-bundles.md`

## 背景

上下文剪枝这类策略（ADR 0020 的候选 `context-pruning`）、MCP 服务器、skill 都要和运行时一起装在 Worker 上。现在 hub 只会装运行时本体（ADR 0010），组件要么靠资产下发（MCP / skill），要么只能用户手动装（pi 扩展、opencode 插件）。手动装的组件 hub 看不见，也没有审核。

## 决定（提议）

1. 运行时套件 = 运行时本体 + 可选组件：运行时插件、MCP 服务器、skill。套件和组件都是 ADR 0016 的资产（kind `bundle` / 组件清单），每个版本都要审核。
2. 组件安装复用 `runtime_job`，加一个新 action，沿用 staging → 校验 → 切换 current → 失败回滚；适配器多实现一个 `ComponentInstaller`。
3. 组件由 hub 预装到 hub 管理的本地目录，锁版本加完整性哈希（强制）。运行时配置只写本地路径，运行时不联网拉包，不自动更新。**安装脚本默认允许**：审核 diff 里展示脚本原文，以 Worker 普通用户身份在 staging 目录里执行，脚本执行记审计；团队 / hub 级可选开关「禁止安装脚本」。残余风险：组件及其传递依赖的脚本能以 Worker 用户权限执行任意代码，哈希只保证装的是审过的版本，不保证这个版本安全。
4. 第三方组件只有 cluster_admin 能审核；个人 / 团队 / 本机 Worker 的安装权限和 `runtime.install` 一致（ADR 0017）。成员往共享 Worker 上装要发申请（ADR 0016 6B）。令牌不能装组件。
5. Worker 上报清单（运行时、组件、版本、哈希、能力）；hub 拿它和 `runtime_pins` / `component_pins` 比较，检测漂移。有漂移的能力调度跳过，修复要人工触发。
6. 组件可以声明能力（例如 `context-strategy:context-pruning@runtime-plugin`），调度只把需要这项能力的会话发给具备它的 Worker。
7. 升级只对新会话生效；默认部分失败只回滚失败的组件，可选「全部或全不」。
8. 第三方组件只有 cluster_admin 审核，可选 2 人审核；外部安装的组件只显示；有漂移的能力调度跳过，人工修复。

## 后果

- 正面：生态组件可见、可审、可调度；ADR 0020 的 runtime-plugin 策略有了落地途径。
- 负面：审核工作量变大；允许安装脚本有残余的供应链风险；每个运行时要写组件安装器；opencode v2 的插件机制还要核对。

## 备选

- 交给运行时自己的包管理（`pi install npm:…`）：pi 启动时会重装装不上的包，用户也可能改动，hub 很难锁版本和审计。
- 组件不进资产审核：第三方代码直接在共享 Worker 上执行，风险不可接受。
