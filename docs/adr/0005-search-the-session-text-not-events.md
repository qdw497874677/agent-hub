# 0005 搜索的单位是会话文本投影，不是事件

- 状态：accepted
- 日期：2026-10-24

## 背景

`journal` 按事件存，`text` 事件是**流式增量**：模型回一句「正交布线做出来」，
库里是 `"正交"`、`"布线做出来"` 两行（实测里一句话能拆成二十几行）。

所以「按行 LIKE」这种搜索对自然语言是失效的：用户搜的是一句话，库里存的是它的碎片。
第一次实现就是按行搜，`E2E-OK` 一条都搜不到——`"E"`、`"2"`、`"-OK-"` 各自一行。

## 决定

**新增读模型表 `session_text(session_id PRIMARY KEY, text, updated_at)`，在
`sessions.append` 的同一次事务里跟随 `text` 事件追加。搜索查这张表。**

- 写：`INSERT ... ON CONFLICT(session_id) DO UPDATE SET text = session_text.text || excluded.text`
- 读：`LIKE` + 转义（`%`、`_`、`\`），命中位置前后各取 60 字做摘要
- 存储代价：会话正文约存两遍（journal 里的 JSON + 投影里的纯文本）。v1 数据量（一年 10⁶ 行内）可以接受

## 为什么不是别的做法

- **搜之前先把 delta 拼起来**（读该会话所有 text 行，在 JS 里 join）：一次搜索要把整个项目的
  正文全读出来。它在 v1 能跑，但成本随历史线性增长，而且每次搜索都付一遍。
- **FTS5 全文索引**：中文要分词、要维护影子表与触发器，而它解决的是「按词相关度排序」的问题，
  我们此刻要的只是「找到那句话」。等真需要排序时再上，届时也换成查 `session_text`，端口不变。
- **把流式合并后再落盘**：等于放弃逐字流式（M2 的验收项），且崩溃时会丢最后一整句话。

## 后果

- 文本投影是 journal 的**派生**，不是第二个权威：`session_text` 坏了可以从 journal 重建
  （重建脚本尚未写，加它是 T2 的账）。
- 一个会话的搜索命中单位是「这个会话」，不是「这条消息」——同一会话里命中十次只出一条。
  这是有意的：搜的是「哪条思路里说过这话」。
- `LIKE` 对大小写不敏感只覆盖 ASCII；中文没有大小写问题，其余语言在 v1 不处理。
