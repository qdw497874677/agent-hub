# agent-hub 产品定位

状态：v1 定位基线。适用于后续设计、用户故事、技术方案与验收，不代表下述能力均已实现。
配套文档：[用户故事](./user-stories.md)、[术语表](../../GLOSSARY.md)、[ADR 0001](../adr/0001-rewrite-hexagonal-core-four-aggregates.md)

---

## 1. 一句话定位

**agent-hub 是运行时无关的 agent 工作台：你自带机器和 agent，它把你的任务拆成多个可并行的会话，并把会话之间的派生与血缘关系变成可见、可恢复的东西。**

拆开读，三句话都必须成立，缺一条这个产品就退化成别的产品：

- **自带机器和 agent** —— 定位是控制层，不是运行时。不卖模型、不卖算力、不接管 loop。
- **任务拆成多个可并行的会话** —— 产品的基本单位是 Session，不是「一次对话窗口」。同一件事可以有多条路径同时试。
- **关系可见、可恢复** —— 画布是这条定位的实现，不是装饰。关掉浏览器再打开，认知不用重建。

## 2. 目标用户

**只服务一类人：重度 AI agent 用户。**

画像很具体：一台机器上装着 Pi、OpenCode、Claude Code 之类的多个 agent，一天里在不同终端之间来回切；常用「同一个问题开三条路试试」的方式工作；痛点不是「不会用 agent」，而是**自己开的会话太多、记不住哪个是哪个、关掉终端就找不回来**。

这类人愿意折腾安装、愿意读配置、愿意自己配模型 key。他们不需要产品替他们做决定，只需要产品别挡路。

**明确不服务**：想用 AI 但不想学 CLI 的普通开发者、需要权限治理的团队、需要托管 key 的企业。理由见 §6 反故事。

## 3. 核心问题

重度用户的损耗不在「能不能跑起来」，而在三处：

1. **并行即失忆。** 同一任务开五个会话试不同方案，一天后分不清哪个会话对应哪条思路、哪个是哪个的后继。终端标签页给不了这个信息。
2. **关掉即丢失。** 终端一关，上下文、运行状态、产出物全部散落。想接着干只能重开、重述、重试。
3. **多 agent 即多套模型。** 每个 agent 自己的会话概念、自己的恢复方式、自己的交互习惯。切换成本高到让人只用其中一个。

这三个问题的共同点：**都不是 agent 能力不足，而是会话资源没有管理面。** agent-hub 做的就是这个管理面。

## 4. 与 wemux-lite 的关系

**agent-hub 是重新设计与开发的产品，不是 wemux-lite 的迭代版本。** 不承诺接口、数据与配置兼容，wemux-lite 降级为「前身与参考实现」。

继承的是**判断**，不是代码与文档：L2 统一事件协议是正确基线、Session 必须绑定 Task、画布必须是真实交互表面而非缩略图。

不继承的是**范围**。wemux-lite 的定位把集群、多用户、授权、治理全部摊了进去（`docs/design/` 下 30+ 份文档、`account-identity-system.md` 单篇 33K、`node-resource-distribution-architecture.md` 63K），结果是每份文档自洽但拼起来没有产品。agent-hub 的反向教训是：**v1 只服务一个用户的一种工作方式，其余能力留端口不留实现。**

## 5. 能力分层

三档，**分档标准是「现在划清边界成本低不低」，不是「重不重要」**：

- **T1 · MVP 闭环必须**：缺了闭环就断了。
- **T2 · 端口在、实现空**：接口与错误语义定义好，实现返回「未实现」。不是半个实现。
- **T3 · 明确不做**：记在这里是为了将来能一眼认出「这是被决策掉的，不是被忘掉的」。

| 能力域 | T1 · MVP 闭环必须 | T2 · 端口在、实现空 | T3 · 明确不做 |
|---|---|---|---|
| 集群与节点 | Server 认多 Worker、Pairing Token、在线状态；单机首次启动自动带一个本地 Worker | 版本与能力协商、撤销节点、远程升级、**资源管理（容量/配额/调度）**、**自动下发安装** | 节点编排与自动伸缩 |
| Agent 与模型 | Pi + OpenCode 两个 L2 adapter、模型切换、**能力矩阵** | 安装与认证自动探测、第三个 adapter、**L1 嵌入原生 TUI** | 平台自持 loop（L3） |
| 项目与环境 | Project = 绑定一个本地目录 | 多目录/仓库、多 Placement | 远端仓库克隆与同步管理 |
| 会话 | 流式输出、停止、恢复、历史 | 消息排队、用量统计、全文检索 | — |
| 画布与血缘 | Task 簇 + Session 节点 + Fork 血缘线 + 布局持久化 + 视图切换 | 更多关系类型（Delegation、Artifact 引用）、多人协同编辑 | 用户自定义节点类型 |
| 任务与交付 | Task 状态、派生 Session、Artifact 归档 | Assignment / Run 分层、审查流程 | 外部 tracker 双向同步 |
| 权限与安全 | 本地单用户 + Pairing Token | Owner / 团队字段（领域模型留位，UI 不做） | OAuth、邮箱注册与找回、审计 |
| 运维 | 一键安装与启动 | 备份与恢复、升级 | 迁移工具 |
| 客户端 | Web + HTTP API（agent 可调 API 建 Task） | CLI、移动端可达路径 | 桌面端打包 |

**关于 T2 里的两项，特别说明：**

- **L1 嵌入原生 TUI** 是「支持不同 agent 并可拓展」这个说法的**下限证明**——如果连嵌入终端都做不到，拓展性就只对写得出 L2 adapter 的 agent 成立。它的降级规则必须现在写清（不能 fork、不能参与 Lineage、不能结构化检索），否则会变成实现时的临时决定。
- **资源管理与自动下发安装** 是明确的未来方向，不是「也许」。所以 T2 而不是 T3：Worker 的注册与指令通道必须从第一天就设计成 **Server 可以向 Worker 下发任意指令**，而不是只够回传执行事件。这条约束是零成本的，漏掉则是重构级的。

## 6. 反故事

这个产品**不**做以下事。写在这里是因为它们每一个单独看都合理，合起来会让产品失去形状：

1. **不替用户管模型 API key。** key 留在用户机器或用户自己的环境变量里。一旦平台持有 key，就变成凭据托管商，要担的责完全不同。
2. **不做多租户隔离。** 没有「组织」「成员」「角色」在这一版。领域模型留 Owner 字段，UI 不做，权限模型不倒推。
3. **不做通用低代码画布。** 画布上的实体类型是固定的（Task / Session / Artifact）。允许用户定义节点类型，就是把产品变成另一个产品。
4. **不做 CI / 部署 / 流水线。** agent 跑测试不是平台跑测试。平台只记录它跑了什么。
5. **不在手机上跑 agent。** 移动端最多是查看与轻交互，执行永远在 Worker 上。
6. **不做 agent 能力的评测与排行。** 「哪个模型更好」不是这个产品的问题。
7. **不承诺兼容 wemux-lite。** 见 §4。

## 7. 架构取向：什么叫「打好底子」

定位层面只承诺四条原则，细节见 [ADR 0001](../adr/0001-rewrite-hexagonal-core-four-aggregates.md)：

1. **六边形架构。** 依赖方向只有一条：适配器 → 端口 → 领域。领域层不认识 HTTP、不认识数据库、不认识 Server/Worker。
2. **领域核心只有四个聚合：Task / Session / Agent / Artifact。** Server 与 Worker 是**适配器**，是「状态存在哪、进程跑在哪台机器上」的部署细节。这条最贵：wemux-lite 把 Server/Worker 当架构一等公民，于是它的领域层被安装形态污染，画布上会混进「机器」这种与产品价值无关的节点。
3. **扩展性由端口承载，不由分支承载。** 新增一个 agent = 写一个 adapter + 填一张能力矩阵，**不改内核、不改 UI 判断**。UI 按能力矩阵渲染，不按 agent 名字渲染。
4. **端口清单先于实现定稿。** 打底子 = 把边界划在正确的位置，而不是把代码写多：

| 端口 | 方向 | v1 状态 | 承载的 T2 |
|---|---|---|---|
| `TaskRepository` / `SessionRepository` / `ArtifactRepository` | 驱动 | 实现 | — |
| `AgentRuntime` | 驱动 | Pi、OpenCode 实现 | L1 TUI adapter |
| `SessionEventStream` | 被驱动 | 实现 | 更多事件类型 |
| `NodeGateway` | 驱动 | 单机直连实现 | 能力协商、远程升级 |
| `NodeProvisioner` | 驱动 | **空实现** | 自动下发安装 |
| `CapacityPolicy` | 驱动 | **空实现** | 资源管理 |
| `WorkspaceFS` | 驱动 | 本地目录实现 | 多目录、远端仓库 |
| `HTTP API` | 被驱动 | 实现 | CLI、移动端 |

`NodeProvisioner` 与 `CapacityPolicy` 的空实现是这次「留扩展点」的具体落点：**接口在、错误是「未实现」、没有代码路径假装能用。**

## 8. 成功判据

v1 成功的定义只有一条，其余都是它的推论：

> **一个重度用户连续工作一天后，第二天打开浏览器，能在画布上认出「昨天哪条思路走到了哪、哪些试过是死路」，并接着干活。**

推论判据：

- 新增第三个 agent 只需写 adapter + 填能力矩阵，不改内核与 UI 判断。
- 单机与多机走**同一条路径**，区别只是 Worker 列表的长度。
- 任何一次会话崩溃后，历史与 Artifact 不丢，剩余状态可继续。
