# agent-hub 用户故事

配套：[产品定位](./positioning.md)、[术语表](../../GLOSSARY.md)

**读法**：主干是按时间序的旅程，**顺序即优先级**——前一个阶段的验收要点不过，后一个阶段不开始。每条故事后标 **T1 / T2**（见定位 §5），T1 是 MVP 闭环必须，T2 是端口在、实现空。每条故事带 2–4 条**可判定**的验收要点，不是完整 Given/When/Then。

角色只有一个：**重度用户**（一台机器跑多个 agent、一天开很多会话的人）。T2 故事的角色是**开发者**或**用户（未来）**，已标注。

---

## 阶段 1 · 起服并看到机器在线

> 目的：让「装起来」这件事的成本接近零，因为这是 v1 唯一的增长瓶颈。

**S1.1**（T1）作为重度用户，我想用一条命令起服务并在 UI 里看到本机 Worker 在线，以便不用先读懂架构就能确认它活着。
- 一条命令完成安装与启动，不需要先手写配置文件或单独配对 token
- UI 在 30 秒内显示 Worker `online`
- 首次启动自动带一个本地 Worker，用户无需知道「Worker」这个概念就能用起来

**S1.2**（T1）作为重度用户，我想在 UI 里看到每个 Worker 的在线状态与来源，以便区分「它挂了」和「我改坏了配置」。
- 状态至少区分 `online` / `offline`，`offline` 附带原因文案
- 每个 Worker 标注其来源（本机 / 远程），便于后续扩展到多机时不自相矛盾

---

## 阶段 2 · 建 Project

> 目的：让 agent 有一个明确的执行语境，同时不引入 Repository / Workspace / Placement 三层填表。

**S2.1**（T1）作为重度用户，我想选一个本地目录建 Project，以便所有 Task 都落在这个目录的语境下。
- 建 Project 只需选目录 + 起名，无其他必填项
- 一个 Project 恰好绑定一个目录

**S2.2**（T1）作为重度用户，我想确认 Project 绑定的是哪个绝对路径，以便避免 agent 在错误目录里跑。
- UI 显示绑定目录的绝对路径
- 目录不存在时**报错**，不静默创建

---

## 阶段 3 · 声明 Agent 与能力矩阵

> 目的：把「支持不同 agent 并可拓展」变成一个可验收的东西，而不是一句形容词。

**S3.1**（T1）作为重度用户，我想选一个 agent（Pi / OpenCode）和一个模型，以便不开编辑器就能开始。
- UI 内可选 agent 与模型，无需手写配置
- 选中的 agent 与模型在 Session 创建前就可见，事后可追溯

**S3.2**（T1）作为重度用户，我想在选好 agent 后直接看到它的能力矩阵，以便知道哪些操作对它可用、为什么不可用。
- 不支持的能力**置灰并给出原因文案**，不是隐藏
- 原因文案来自能力矩阵，不来自按 agent 名字分支的硬编码判断

**S3.3**（T2）作为重度用户（未来），我想让平台自动探测本机已安装的 agent 与已登录状态，以便不用手填。
- 端口存在；未实现时返回「未实现」而不是假装探测成功

---

## 阶段 4 · 建 Task

> 目的：确立「Task 是会话的唯一来源」，这是全产品最硬的一条领域规则。

**S4.1**（T1）作为重度用户，我想建一个 Task（标题 + 目标）并立刻在画布上看到它，以便任务成为会话的锚点。
- 建 Task 只需标题；目标可选
- 保存后画布上立即出现该 Task 的节点/簇，无需刷新

**S4.2**（T1）作为重度用户，我想改 Task 的状态（进行中 / 完成 / 放弃），以便区分「还在试」和「试过是死路」。
- 状态在画布上可直接读出，不需点开详情
- **放弃的 Task 不隐藏也不删除**——死路记录本身就是产品的价值（见定位 §8 成功判据）

**S4.3**（T2）作为重度用户（未来），我想把 Task 拆成 Assignment / Run 两层，以便同一目标分派给多个 agent 竞争。
- 端口与领域模型留位；UI 不做

---

## 阶段 5 · 派生 Session 并看到流式输出

> 目的：把「从任务派生会话」做成唯一入口，杜绝无主的聊天窗口。

**S5.1**（T1）作为重度用户，我想从 Task 派生一个 Session，以便在任务语境下开一条尝试路径。
- 画布上出现 `Task → Session` 连线
- **产品不提供无 Task 的新建会话入口**——这是领域规则，不是 UI 偏好

**S5.2**（T1）作为重度用户，我想在画布节点里直接看到流式输出并回消息，以便不离开画布就能推进。
- 节点内可发送消息、看到流式文本、看到工具调用
- 交互不跳转到另一个页面，不丢失画布布局

**S5.3**（T1）作为重度用户，我想停止一个正在跑的 Session，以便它跑偏时立刻止损。
- 停止后 Session 进入明确终态，不是「假装停了但仍在跑」
- 停止一个 Session 不影响同 Task 的其他 Session

---

## 阶段 6 · 多会话并行与 Fork

> 目的：**这是产品成立的分水岭。** 多会话并行 + 血缘可视化是「画布」存在的唯一理由。

**S6.1**（T1）作为重度用户，我想对同一个 Task 派生出第二个 Session，以便并行试不同方案。
- 两条以上 `Task → Session` 线并存且视觉可区分
- 兄弟 Session 的上下文**不共享**，互不污染

**S6.2**（T1）作为重度用户，我想 Fork 一个 Session，以便从某个中间点换方向而不重述上下文。
- Fork 记录**来源 Session + 固定的事件游标**
- 来源 Session 之后的续写**不自动进入** Fork 目标的上下文

**S6.3**（T1）作为重度用户，我想在画布上看到 Session 之间的血缘线，以便认出哪条思路从哪来的。
- 血缘线可区分 `derive`（来自 Task）与 `fork`（来自 Session）
- 节点可拖动，布局持久化

**S6.4**（T1）作为重度用户，我想在画布 / 专注对话 / 列表之间连续切换，以便排布时看全局、深入时看细节。
- 切换保留草稿、滚动位置、待发送队列与执行状态
- 列表是画布的低成本降级形态（搜索与移动端可达性靠它），且**不做看板**

---

## 阶段 7 · 关闭再打开，全部还原

> 目的：**这是「能持续用」的分水岭。** 否则每次重开都要重建认知，产品价值归零。

**S7.1**（T1）作为重度用户，我想关掉浏览器再打开看到全部还原，以便第二天接着干。
- Task、Session、Lineage、Artifact、画布布局全部还原
- 关闭前仍在运行的 Session，重开后标记为**「中断」而不是「运行中」**

**S7.2**（T1）作为重度用户，我想让会话的 Artifact 挂在 Session 上并汇总到 Task，以便产出不散落。
- Artifact 可从 Session 侧与 Task 侧两个方向看到
- 任一 Artifact 可定位回产生它的那个 Session

**S7.3**（T1）作为重度用户，我想在 Session 崩溃后恢复而不是重开，以便不丢已发生的上下文。
- 崩溃后历史完整可读
- 剩余状态可继续（续写）或明确终止，不存在「半死不活的运行中」

---

## 阶段 8 · 第二台机器接入

> 目的：闭环之后的第一件事。**单机与多机是同一条路径，区别只是 Worker 列表的长度。**
>
> **S8.1 已从 T1 移出（2026-11 决定）**：MVP 的定义是「单机闭环」。多机引入的是部署变量，不是产品变量——闭环未证明前先加它，是在给未验证的东西加自由度。S8.1 成为闭环验收后的第一个 milestone，见 [MVP 实现计划](../plan/mvp-plan.md)。

**S8.1**（闭环后）作为重度用户，我想用 pairing token 让第二台机器加入，以便把 agent 跑在更强的机器上。
- 走与单机完全相同的机制，不启动第二套服务
- 加入后可在该 Worker 上派生 Session，画布无需新概念

**S8.2**（T2）作为重度用户（未来），我想让 Server 向 Worker 下发安装与升级指令，以便不用逐台 SSH。
- `NodeProvisioner` 端口存在；调用返回「未实现」
- Worker 的连接与指令通道从第一天就设计成**双向可下发**，不只回传执行事件

**S8.3**（T2）作为重度用户（未来），我想设置容量与配额策略，以便一台机器不被跑满。
- `CapacityPolicy` 端口存在；调用返回「未实现」

---

## 跨切面约束（架构底子的可验收形态）

**X1**（T1）作为开发者，我想新增第三个 agent 只写一个 adapter + 填一张能力矩阵，以便「可拓展」不只是说法。
- 新增 agent 后，**内核与 UI 判断零改动**
- 有一份对照检查清单，列出「新增 agent 需要动的文件」

**X2**（T1）作为开发者，我想让领域层不依赖 Server / Worker / HTTP / 数据库，以便架构不随时间腐化。
- 领域包的依赖图只有端口，CI 里可检查
- Server / Worker 只出现在适配器层与装配处

**X3**（T1）作为用户，我想让 agent 通过 HTTP API 建 Task、派生 Session、读 Lineage，以便 agent 自己组织工作。
- API 覆盖：建 Task、派生 Session、读 Lineage、读 Artifact
- Agent 与人走同一套领域规则，不设特权旁路
