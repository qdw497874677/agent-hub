# 项目 Git 授权：空白 Worker 上的会话 Git 操作

状态：按阶段本地实施。Hub 侧登记仓库的 HTTPS 只读检查已接入独立、默认关闭的接口；本页的抓取与无凭证对象导入尚未接入会话工具或部署。另有 [Hub 托管凭证](hub-credential-broker.md) 首版，满足条件时默认开启，可直接读取远端快照，不走对象导入路径。现有 Git 工具见 [agent-git-tools.md](agent-git-tools.md)，精确提交审批见 [workspace-delegation.md](workspace-delegation.md)。

## 目标与边界

选定一台没配 Git 凭据、没配 SSH key、没跑 ssh-agent 的 Worker，Agent 仍能通过会话内 MCP，使用项目授权访问已登记的仓库。不让 Agent 获取凭证明文，不把仓库 URL、文件系统路径或任意 Git 命令当作授权范围。不改变「仅对话」的语义：启动不接触仓库，不执行准备命令。

现在的 Worker 和 Agent 进程共享运行账号，部分 Runtime 继承 Worker 环境。HTTPS 项目令牌虽然已按目标附加给 Git，但单次子进程、临时文件或环境变量不是同账号隔离边界。**在凭证执行器与 Agent 进程隔离前，不对可执行任意 shell 的会话开放新的项目凭证能力，也不把现有路径当成隔离保证。** 可信机器管理员仍能管理主机；不承诺抵御 Worker 主机或 Hub 被管理员级别攻破。

## 1. 项目登记：仓库决定目标和认证模式

沿用项目仓库的 `projectId + repoId` 身份，配置克隆地址、默认分支及以下一种认证模式：

| 模式 | 凭证来源 | 适用于空白 Worker |
| --- | --- | --- |
| 隔离项目 HTTPS | 与兼容模式分开的 Hub 专用凭据 | 只读检查已实施；对象交付已在测试中验证，尚未启用 |
| 项目 SSH | Vault 中仓库专用 SSH 凭证；登记经可信渠道核对的服务器 host key | 是，前提是 Git 服务接受该凭证 |
| 机器凭据 | Worker 服务账号自己的 Git/SSH 配置，作为显式兼容模式 | 否 |

SSH 优先使用专用、默认只读的部署密钥。不复用员工个人私钥或 IDE 身份；用户在代码托管端授权公钥。保存凭证只写不回，表单只显示配置状态和最近一次检查结果。更改仓库地址、认证方式、host key 或轮换凭证使旧检查失效；每次使用时重新读当前配置。项目凭证不可用时明确失败，不静默切换地址、协议或机器凭据。

兼容模式的「检查」用选定 Worker 和既有凭据路径。隔离检查只访问已登记的 HTTPS 仓库，由独立 Hub 执行，只验证仓库可读和登记分支是否存在；两者均不据此推断可推送，也不把检查成功当成后续授权。AntCode 需先确认项目部署密钥能否独立使用；如必须由 IDE 透传专有身份，则标记该认证方式尚不支持，不做隐式转发。

兼容检查失败时，可在仓库行展开并复制「查看诊断」中的编号、凭据来源、失败阶段、传输方式、耗时和可确认的错误类别。凭编号可在 Hub 的 `project.repos_check` 审计记录中对应到这次检查。不复制仓库地址、令牌或原始 Git 输出；只有 Git 明确报告 HTTP 状态时才显示状态码。若 Git 只报无法提示输入用户名，结果是认证原因未明，不等于令牌失效，也不能确认分支不存在。

## 2. 执行器：凭证和 Agent 工作区分离

1. 会话 MCP 请求只提供 `repo_id`、可选分支、稳定请求键等结构化输入。Hub 从工具授权和会话来源解析项目，再从项目配置取标准仓库目标；调用方不能传 URL、凭证名或机器路径。
2. Hub 每次重查当前账号、会话归属、仓库操作许可和 Worker 可用性。首版把**带凭据的操作**放在不运行内嵌 Worker、且不与 Agent 共享账号/凭据目录的专用 Hub，Worker 仅可接收不带凭据的已核对 Git 对象；后续可在不改变操作契约的前提下替换为等价隔离执行器。旧 Worker 或未启用隔离的 Worker 明确拒绝对象导入，不回退到已有的带凭据 RPC。
3. 执行器独立于 Agent 的 OS 身份与可访问目录；任务凭证只存在于执行器控制的短期上下文。仅接受经 Hub 授权、带目标和操作约束的请求，Agent 不能直接访问凭证文件、进程环境、IPC 或签名接口。普通 Worker 启动 Agent 时不下发项目凭证。SSH 私钥不写进会话目录，不向会话转发 ssh-agent；验证登记的 host key，未知或变更就失败。HTTPS 使用正常 TLS、精确目标绑定、禁止重定向，禁用环境和本地配置对目标或凭证的改写。
4. **带凭证的 Git 不在 Agent 可写的仓库里执行。** 执行器使用隔离的 Git 暂存，远端、Git 配置和上下文由平台生成，不加载会话的配置、hooks 或外部 helper；首版不递归子模块，也不加载额外下载过滤器。凭证阶段结束后才交付对象或检出到获准工作目录。更新会话端引用须按指定远端及分支进行，不改 `HEAD`、当前分支、索引和工作文件。发布则反向把已审批的确切对象交给执行器，不接受会话提供的远端配置。

审计记录账号、会话、项目、仓库、Worker、动作、目标引用/SHA 和结果，不记录凭证或未经脱敏的 Git 输出。远端写入结果不确定时先核对，不自动重放。

## 3. 会话权限：操作分层，不扩大默认授权

| 能力 | 首版行为 |
| --- | --- |
| 查看状态、历史；创建本地分支、暂存与提交 | 普通本地 Git；限定在会话自身工作目录，不需要项目远端凭证 |
| `git_fetch` | 新增会话内 MCP；已绑定的仓库、已授权的会话工作目录；只更新指定远端引用，返回抓取的 SHA，不自动 merge/rebase/checkout |
| 显式下载仓库 | 复用工作区创建流程。多仓须选 `repo_id`，新建受管目录，不覆盖已有内容；「仅对话」不会自动下载。首版不热切换运行中的 cwd；要在下载目录开发，可以显式从该目录开会话 |
| 推送、创建 PR | 独立授权；复用现有按项目/分支的写入检查和派工的人工精确 SHA 审批。项目读凭证不等于远端写权限；PR 平台 API 凭证仍独立。禁止自动合并和强推 |

首版仅对明确启用能力的普通人类会话开放新的网络读取工具。Bot、共享会话和受限派工子会话不继承项目凭证能力；隔离执行业务稳定后，再考虑为具体派工单独授予仓库只读能力。既有 Worker 账号的 Git 凭据与任意 shell 不在 MCP 授权控制之内；隔离模式须确保 Agent 进程也没有继承这些凭据，不能用工具权限替代运行时隔离。

## 实施及验收顺序

1. **先做隔离执行路径和 HTTPS 只读**：统一检查、受管下载和 `git_fetch`。用隔离证书的本地私有 Git 服务及一台无凭据 Worker，验证真实 MCP 调用、仓库/分支鉴权、凭证轮换、跨项目和工作目录拒绝。验证 fetch 前后 `HEAD`、索引和未提交文件不变，且 Agent 侧看不到凭证。
2. **再做项目 SSH**：复用同一操作契约，加入部署密钥配置、服务器 host key 核验、吊销和轮换。以空 `HOME`、无 ssh-agent 的 Worker 验证正确项目密钥可读、错误或撤销的密钥不可读、主机密钥变化被拒；最后在明确授权的 AntCode 测试仓库验证服务端实际支持情况。
3. **最后迁移远端写入口**：仅在明确授权的测试仓库验证已批准 SHA/目标分支能发布，未经授权或 SHA 已变更则拒绝；未取得隔离能力的 Worker 不回退到普通推送。现有行为保留兼容入口，不以这次设计宣称全平台 shell 受限。

### 第一个增量：登记仓库的 HTTPS 检查

- 默认关闭。仅当 `HUB_SPAWN_WORKER=0`，运营方同时设置 `HUB_PROJECT_GIT_PROBE_ORIGINS`（逗号分隔的精确 HTTPS origin）和 `HUB_PROJECT_GIT_PROBE_PROJECTS`（精确项目 ID），并预建由 Hub 当前用户拥有、组和其他用户无权限的真实数据目录（建议 `0700`，不能是符号链接）时，才装载独立路由。Hub 不替运营修改权限；这些检查不代替主机或账号隔离。
- 项目设置的现有 Worker 检查不走这个入口。隔离 API 只接受浏览器登录、当前项目写权限和已登记仓库 ID；凭据使用 `PUT /api/projects/:projectId/repos/:repoId/isolated-credential` 写入专用加密表，`DELETE` 撤销。`POST …/isolated-check` 不接受目标参数，只读取登记地址的 Git 分支广告。结果不回显凭据或原始 Git 错误。
- 专用凭据不出现在资产展开、普通 clone/fetch/push 或 Worker RPC 中；地址变更后旧凭据不再匹配。既有兼容入口和其独立凭据没有被迁移或改变。

### 第二个增量：抓取和候选对象交付（本地验证）

- Hub 从精确登记的 HTTPS 地址抓取指定分支的完整历史，不递归子模块、不抓取标签。Git 子进程只访问一次性的本机 HTTP 桥，项目凭据留在 Hub 的 HTTPS 出站请求中。浅抓取不用于交付：`git bundle verify` 通过不代表空仓库能恢复完整历史。
- bundle 携带精确分支 tip 和 SHA-256；Worker 在空的暂存仓库验证对象可恢复后，只在授权工作目录建立 `refs/agent-hub/fetch/<projectId>/<sha>`。不检出、不合并，不更新 `HEAD`、索引或远端跟踪分支。首版导入只支持普通仓库，链接 worktree、浅仓库和部分克隆明确不支持。
- 本地验收用私有 TLS Git 服务抓取两个相连的提交，再经真实 Worker WebSocket 交付。目标能读取完整历史，远端 refs、工作区 `HEAD`、索引和未提交修改均不变。同一请求键只读 SQLite 回执，不重复访问远端或导入；结果不明则不自动接管或重放。RPC 只在 Worker 显式注入导入器时启用；原始包限 8 MiB，普通 Worker 启动入口尚未接入。
- 网络和包体积限制不等于解包磁盘配额。凭证执行器的运行用户、数据目录、磁盘配额仍是启用会话工具的硬门槛；未满足时不启用，不回退到把凭据发给 Worker。

### 启用前的部署验收

- 首个支持配置采用两台独立机器或虚拟机。Hub 不执行 Agent，使用专用、非特权服务账号和私有数据目录；Worker 不挂载或共享 Hub 的目录，也不继承 Hub 的项目凭据。给同一账号换个进程、临时目录或容器名字不算隔离。
- Hub 抓取及 bundle 暂存、Worker 验证暂存、实际写入的目标对象库都必须落在受硬性空间上限约束的存储上。不能拿 `statfs` 的剩余空间、压缩包上限或环境变量当成配额证明。临时包由调用方在验收成功或失败后清理，并为意外中止留下的文件设清理机制。
- 启用前验证：运行 Agent 的身份不能读取 Hub 数据；向限额目录写入超限触发实际拒绝；导入受限时不报告成功、不建候选引用、不修改 `HEAD`、索引或工作文件；不具备能力的 Worker 收不到导入请求。源码中的合成 HTTPS 和 WebSocket 集成测试只证明链路，不证明真实部署隔离或配额。
- 本地可用 `HUB_TEST_BWRAP_QUOTA=1 node --test e2e/project-git-bundle-quota.test.ts` 分别验证暂存区、目标对象库空间耗尽。Linux 测试以小容量 tmpfs 复现真实写入拒绝；它不代替对部署上持久目录和运行身份的验收。Worker 导入器的 `scratchRoot` 只指定暂存位置，不会创建或证明配额。
