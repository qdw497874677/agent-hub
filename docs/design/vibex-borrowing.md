# VibeX 借鉴实施计划

**状态：第一期已合入 `06e24d6`；第二、三期已通过本地验证，尚未部署。** 本轮 [T3 Code 借鉴](./interaction-borrowing.md) 的工作台导航、可撤销整理、任务归档和全局查找，以及多仓建项目，已在 `9a1e863` 验收并部署：2,985 项单测通过、8 项跳过，13 项浏览器测试通过。VibeX 只补验收后仍存在的缺口，不改变建任务与启动会话分开的流程。实际操作见[工作台本轮验收](./workbench-acceptance.md)。

目标：让用户在现有的任务、会话和画布里看清 **会话实际跑在哪里、为什么停了、交回了什么、验收对应哪个提交**。参考 VibeX `18f1ad7` 的交互与语义，不复用 AGPL 源码。

## 范围：七项，分三期

| 编号 | 借鉴项 | 落点与验收标准 |
| --- | --- | --- |
| V1 | 问询／审批原位留痕 | 在会话内使用现有授权与处理入口；处理后原位置显示终态，有权限的人可回看。窄屏不需要往返待办页。回合耗时只在有可靠起止记录时显示；计划进度只显示 Agent 上报值，不代表任务完成度。 |
| V2 | 启动前确认实际运行配置 | 在现有启动区域集中显示机器、工作目录、Agent、模型；建任务与启动会话仍是两步。配置不可用或未选时明确提示，不自动猜机器。若 T3 已覆盖，则保留现状、只记录验收证据。 |
| V3 | 评审导航与 diff 阅读分开 | 复用 T3 落地的 diff 范围和读取能力。版本／文件列表负责导航，正文负责读 diff；手机返回保留已选版本及文件，不把 diff 塞进画布节点。延续现有敏感文件过滤。 |
| V4 | 执行结束与人验收分开 | 同一张派工详情显示执行阶段、阻塞原因和验收状态；有实际关联才链接会话、候选提交或测试报告。子会话结束不自动完成任务，也不自动发布。 |
| V5 | 结果未知与失败分开 | 仅在已有证据能区分时显示「结果待确认」或「失败」；断线、超时本身不证明失败。未知时引导查看原记录，不自动重放、不显示通用重试；没有执行会话则不显示打开入口。 |
| V6 | 交接清单写实际交付 | 复用结构化交接记录展示已发送的说明、附件与完整候选 SHA；未记录、不允许查看与未交付不可混为一谈。不默认复制整段会话。后续若支持片段引用，需另验权限、范围和截断。 |
| V7 | 验收精确绑定 SHA | 在派工详情和评审上下文显示测试证据对应的 SHA。当前 HEAD 变化时，保留旧版证据，但不标新版已通过；拿不到 HEAD、SHA 或测试证据时标为无法确认。分支名和会话结束均不是验收证据。 |

## 实施顺序与验证

1. **第一期：会话内闭环（V1、V5；复核 V2）。** 先核对问询、审批、运行状态与交付记录的持久事实；不从本地按钮状态推断处理成功。Playwright 覆盖问答和审批处理后原位留痕、刷新、窄屏操作，以及未知结果无重试／无虚假会话入口。若现有记录不足，先补最小的持久证据和权限测试。
2. **第二期：派工交接与验收（V4、V6、V7）。** 在现有派工详情合并展示，不新增三个入口。先复用已有的派工、候选交接和精确发布记录（见 [工作空间派工](./workspace-delegation.md)、[项目会话 MCP](./project-session-mcp.md)）；如果缺少人工验收或结构化测试证据，先写清最小记录与授权再实施，不能从聊天文字推断。验证结束后仍待验收、无权不可读、候选 A 验过而 HEAD 变化到 B 时不继承结论，并覆盖刷新后状态一致。
3. **第三期：评审阅读（V3）。** 复用现有 diff API，把移动端的返回列表与清除所选文件分开。当前可用范围是会话基线、HEAD、默认分支共同基线和已记录的回合检查点：前三者比较当前工作树，回合比较前后快照；不能当成任意 Git 版本。只在进入阅读时取选中文件，不预取其他文件或范围，不重做 Git 服务或发布流程。Playwright 覆盖切范围、切文件、手机返回与桌面；后端回归确认单文件路径按字面量处理、敏感内容仍拒绝，并保持会话及工作区现有权限。

每期独立验收：`npm run check`、`npm run typecheck`、`npm run typecheck:web`、相关单测；改到浏览器交互必须用独立端口和全新数据目录跑相关 Playwright spec，记录命令、退出状态和结果。涉及 Worker、Git 或持久状态时另做对应的真实本地链路验证；不以生产数据或真实凭据作为验收前提。

第一期的证据边界：审批以同一个请求 ID 的持久解决事件为准；普通消息不自动归为某个问询的答复。适配器没有上报的问题、计划进度或真实起止时间，不补造记录，也不把审批等待时间当运行耗时。未知结果不自动重发，用户仍可通过正常输入框发起明确的新回合。

### 第二期的最小记录与授权

- **交接**读取现有结构化消息，只认 Hub 已绑定到本派工执行会话、同一项目及仓库的候选记录。普通发送也能写 `data.schema` 和自选幂等键，因此两者都不能证明消息由交接入口生成；如果现有记录没有可信来源字段，只给新记录增加由 Hub 写入的来源，不为历史消息猜测来源。读取每条消息或附件沿用现有权限；不能确认读取范围时不把空结果说成「未交付」。普通文本里的提交号、任意 `data` 消息里的自称及导入成功都不算测试证据。
- **人工验收**单独保存派工 ID、完整 SHA、验收人、时间和可选备注，不修改任务状态，也不触发发布。追加记录不可覆盖；同一请求键只能重放相同内容。首版沿用派工所有者可见范围，并额外检查当前会话可读和任务更新权限，不借此打开团队级派工详情；协作者共享验收另设计。
- **当前性**用 Worker 验证该派工工作树及完整 HEAD，不能拿基线、分支名或历史发布 SHA 替代。提交时重新读取；SHA 不符不落记录，Worker 无法核对时不落记录。历史验收依然属于原 SHA；HEAD 无法确认或已变化时，不显示「当前已验收」。这次核对不是锁住工作树，读取时也必须说明当前性。
- **测试证据**首版没有可信测试结果协议，不从 `verify-result/v1` 普通数据部件推断测试通过。人工验收和自动验证分别呈现；无可信报告时明确显示「未记录」，不能把人工验收标成测试通过。

第三期安全回归：单文件 diff 的路径必须按字面量处理，不接受 Git 路径匹配语义；验收同时覆盖工作树比较和回合快照。文件名与变更计数是既有列表行为，不等同于允许展示正文；导航改动不增设敏感正文预览入口。
