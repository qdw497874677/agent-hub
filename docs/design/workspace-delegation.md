# 持久工作空间派工：实施计划

会话内直接使用项目级工具（资产、任务、worktree 会话与交接）的后续方案见[项目会话 MCP](project-session-mcp.md)；本文描述已有的派工提案及独立发布审批路径。

## 目标和产品边界

用户手动在项目的长期工作空间开一条主会话，平时只在这条会话工作；需要分工时，从主会话提出派工，平台给执行会话开独立 worktree。主会话和人都能查看进度、追问、要求修改和中断。执行会话交付测试结果、提交 SHA 和 PR；主目录不为派工切分支，不继承执行目录的改动。持久的是工作空间和会话记录，不承诺 Runtime 进程永远在线。

主会话由人手动启动，不要求创建 Bot；可以不归任务，使用创建时写入的不可变 `originProjectId`。派工时由人选择现有的同项目目标任务；Agent 不获得自行指定任意任务的权力。执行会话必须归目标任务，以便记录 PR、工作日志和资源所有权。暂不做跨项目、自动合并、多仓一起发 PR，也不自动分发凭据。

## 当前底座和差距

- 手动开始入口要求 `taskId`，项目画布从任务关联查询会话，首页也排除无任务会话。给无任务主会话开放派工，不是把一个字段改为可选；需要验证创建入口、可见性、可操作权限和消息路由（`packages/contract/src/wire/http.ts:194-229`，`packages/storage-sqlite/src/store.ts:338-341`，`packages/domain/src/use-cases/home.ts:60-82`）。下一次提示可通过 Runtime 支持的恢复机制继续，不承诺后台进程跨重启存活（`packages/domain/src/use-cases/hosting.ts:16-78`）。
- `agent.spawn` 已能为**当前任务**开同级会话，`workspace_mode=isolated` 或 `repo_id` 可建独立 worktree，`handle` 和自动连线可用于 `agent.ask`；目前不能传目标任务。它没有持久派工记录，也没有传入 `parentSessionId`；不要把自动连线算作派工血缘。既有 Bot dispatcher 不是替代方案，它默认复用长期工作目录（`packages/domain/src/tools/agent-orchestration-tools.ts:140-157,224-267`，`apps/server/src/wire-tools.ts:142-206`，`apps/server/src/wire-connectors.ts:302-333`）。
- worktree 支持从 `task.baseBranch` 或仓库默认分支派生，但 PR 当前使用实时检测的远端默认分支作为 base。非默认基线的派工不能直接承诺正确提 PR（`packages/domain/src/use-cases/temporary-workspaces.ts:133`，`packages/domain/src/use-cases/workspace-groups.ts:610-641`，`packages/domain/src/use-cases/git-workflow.ts:254-262`）。
- `git.pr` 可能先提交和推送，再建 PR；比较链接不是已建 PR。共享会话的 Git 写入已经拒绝，而且冻结的 `createdBy` 不能代替当轮人的授权。新派工不能依赖普通会话的历史 owner 回退取得权限（`packages/domain/src/tools/git-tools.ts:61-115`，`apps/server/src/git-write-identity.ts:40-66`）。
- 已有 worktree 准备路径允许 fetch 失败后继续；普通临时空间路径还可能复活历史目录或退化为非 Git 目录。这次的显式派工不接受这些降级：目标远端不能确认、base 获取失败或旧分支归属不明时停止并报告（`packages/node-gateway/src/git-workspace.ts:156-157`，`packages/domain/src/use-cases/temporary-workspaces.ts:101-137,141-165`）。

## 实现顺序

1. **先固定身份与目标。** 从可见的主会话发起，明确项目、任务、仓库、机器、基线分支和执行说明；由服务端确认人对任务、机器和仓库的权限，并归属到可审计的主会话与执行会话。区分父子血缘（谁派工）与消息连线（谁能互通），不因连线扩大任务或仓库访问权。先验证所选 Runtime 能发现并调用工具，缺工具时保留人从工作台发起的路径。
2. **可靠地创建并交接。** 复用现有 worktree 和会话入口；为一次派工保存稳定请求身份、目标任务、实际 worktree、执行会话、源仓库与基线 SHA。每次派工独占工作树和功能分支；重复提交复用结果，准备失败可恢复或明确失败，不静默换仓库/分支。Hub 或 Worker 重启后显示可查状态，不因状态未知重复发任务；不自动重放 Git 写操作。
3. **把交付接回工作台。** 在主会话和任务里都能定位执行会话、分支、测试结果、提交与 PR。复用消息和任务记录；支持追问、回退修改和中断。先证明现有画布/导航能表达跨任务父子关系，再决定最小 UI 增量。取消不等于已停止，不在执行结果未知时清理。
4. **默认由人确认发布。** 执行会话产出并报告测试和提交候选；手动批准 `push + 创建 PR` 时，Hub 再校验项目权限、仓库、工作树、功能分支、base 与预期 head SHA；不隐式提交未审阅的修改。GitHub 返回实际 PR 编号和 URL 才记为成功；远端超时先核对已存在的 PR，不盲重试。允许一次性授权后自动发布作为后续增强，范围限单次派工和操作；不改变共享会话、默认分支的现有写入限制。这个步骤不能退化成「复制两条 shell 命令」作为首版验收。
5. **清理后置。** 首版允许人按既有安全检查显式清理；仅对临时 worktree 生效。主空间以及忙碌、脏、未推送或归属不明的 worktree 都保留，显示原因。不迁移或推断历史孤儿归属。

## 验证门槛

| 证据层 | 责任 | 必须证明 |
| --- | --- | --- |
| 领域 / 存储 | 后端 | 主会话、任务、仓库、机器权限分别覆盖；跨项目/过期或被撤回授权拒绝；并发双击和进程重启不重复起会话；准备中途失败可诊断及安全重试。 |
| Hub + Worker + 真实 Git，临时仓库 | 后端集成 | 从指定 base 建两个并发独立 worktree；主目录 HEAD 与工作树均不变（含未提交改动）；校验 SHA 后发布，拒绝错误仓库、已变更 HEAD 和默认分支；模拟 GitHub 超时后复查，任务只记录一条真实 PR。 |
| 浏览器 Playwright，独立数据 | 前端 | 手动开主会话 → 派工 → 查看执行会话 → 双向交互 → 看到测试和 SHA → 明确批准 → 看到目标任务 PR；再覆盖拒绝和中断，不用 UI 文案替代实际数据库或 Git 状态。 |
| 专用测试仓库 / 测试账号 | 发布验收 | 至少一套受支持 Runtime 真调用工具并交付草稿 PR；不用生产令牌或生产仓库，不自动合并。 |

### 本地浏览器 + 真实 GitHub 验收清单

1. 在专用仓库 `qdw497874677/agent-hub-connector-e2e` 准备默认分支 `main`。用两枚仅限该仓库的短期令牌：Contents 读写用于项目仓库，Pull requests 读写用于测试团队。只在隔离 Hub 的设置页录入，不发到聊天、不写入日志，Worker 不预置仓库写凭据。
2. 在浏览器打开本地 Hub，在长期工作区新建主会话。从主会话提出派工，确认前检查没有创建执行会话、工作树或分支；由人在页面确认，然后打开执行会话，检查改动只落在独立工作树，主工作区不变。记录所用 Runtime；如用 ACP 测试进程，只算真实 GitHub 发布验收，不算真实模型验收。
3. 在页面复核并批准完整的 40 位 SHA，从 Hub 发起发布，不用命令行代推。打开返回的 GitHub PR 页面，检查目标仓库、草稿状态、base 为 `main`、head 为本次派工分支、head SHA 与批准一致。不合并；同一批准重试不得重复建 PR，结果不明时只走对账。
4. 报告记录 Runtime、派工 ID、批准 SHA、PR 链接和通过项；不记录令牌。以上结果与使用替身的 Playwright / 本地系统 E2E 分开汇报。

## 复审决议和交付门禁

- **A：建链。** 专用的人类主会话与派工入口，不泛化 `agent.spawn`。项目来源只走不可变字段；消息先用显式关联和 `session:<id>`，父子关系由派工记录表达。主会话的 Runtime 可以登记同项目提案，但不能创建工作树、启动执行会话或发布。人确认时只提交提案 ID；Hub 重新校验权限，再按持久化的原始配置执行。执行会话不继承平台 Git 写权限。第一阶段可独立验证派工，不视为完整交付。
- **B：交付。** 加专用的人工确认发布入口。Executor 可在隔离目录生成本地提交候选；若需要平台代提交，必须有独立的显式操作，发布不替它补提交。Hub 以确认的 head SHA 创建尚不存在的功能分支，不覆盖任何已有远端提交；远端已经是同一 SHA 时只核对。用派工记录里的基线分支建草稿 PR，同时核对仓库、head 和 base。核对只证明当时的 head，不会把 GitHub PR 永久锁在该提交。结果未知时先查证；旧 `git.pr` 不复用为发布端点。审批只约束平台凭据；阿里云测试 Worker 不预置能绕开流程的仓库写凭据。
- **恢复边界。** 每次派工在产生外部副作用前持久分配唯一记录和执行身份；步骤不明时停止并提供核对入口，首版不承诺崩溃后自动继续，也不能在同键重试时再创建执行会话。一个任务可有多个派工，不覆盖 `Task.branch` 来表示分支。
- **发布门禁。** A、B 和本地端到端全部通过后，才进入阿里云验证。代码需要部署时先明示 Hub/Worker 重启影响并按兼容顺序上线；真实 PR 只用专用测试仓库、测试权限和草稿模式。没有可写测试仓库或适用账号时报告外部阻塞，不以生产仓库替代。

发布重试使用原批准键；仍在发布、结果未知或已成功的派工不能换键再发。发起人即使是最初的派工者，也必须在批准时仍有该项目的推送权限和该 Worker 的使用权限。对账只核查远端，不推送或创建 PR。
