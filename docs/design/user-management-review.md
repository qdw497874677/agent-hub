# 用户管理现状评审与优化建议（2026-10-29，基于 master d39676f）

> 只做分析，没改代码、库和服务器。

## 一、现状

**已有的功能**
- 角色只有 `owner` 和 `member` 两种，是 hub 级的隐式 Workspace。按 ADR 0008，账号“不做资源隔离”（`packages/domain/src/account.ts:3,11`）。
- 注册：第一个注册的人原子地认领 Owner。之后的人受 `openRegistration` 和 `HUB_MAX_USERS` 约束，停用的账号也占名额（`use-cases/accounts.ts:97-137`）。
- 密码按 NIST 规则：至少 10 位，再过一个常见弱口令表。哈希用 scrypt，登录失败时有防计时的 decoy（`accounts.ts:146-158`）。
- 邮箱验证和重置密码用一次性令牌，库里只存哈希，30 分钟过期。重置成功后会踢掉所有登录并发通知（`use-cases/account-email.ts:53-100`）。没验证邮箱的人只能访问账号接口（`apps/server/src/auth.ts:166`）。
- 登录态：httpOnly cookie 加 CSRF 双提交，30 天滑动续期，库里只存令牌哈希。有设备列表、踢单台设备、踢其他设备（`auth.ts:269-290`）。
- 后台（`apps/server/src/admin.ts:91-188`，都要求 Owner）：用户列表和搜索、停用和启用、手动标记已验证、踢某人的全部登录、改角色（“最后一个主人”受保护）、hub 设置、审计日志。
- 限流：进程内存里的固定窗口计数。注册按 IP；登录按“IP+邮箱”；发信按多个 key（`rate-limit.ts`、`auth.ts:130-137`）。
- 审计覆盖用户、设置、机器、运行时、项目删除、资产这几类写操作（`account.ts:126-150`）。

**缺口与风险（按严重程度）**
1. **【高】项目、会话、任务完全没有归属和权限。** `deleteProjectUseCase` 只检查“已登录且没停用”（`use-cases/delete-project.ts:28-35`），任何成员都能删任何项目，这就是 默认项目 被删的原因。设计文档 `docs/design/accounts.md §8` 写的是“成员仅能删自己创建的”，实现跑偏了：Project 上根本没有 `createdBy`，只有 Task 有 `ownerId`（`domain/src/task.ts:21`）。
2. **【高】成员可以在任何在线 Worker 上开会话，包括 Owner 的“本机”Worker。** 成员因此等于能在 hub 服务器上执行代码、读 Owner 的工作空间。只要开放注册，就是“注册即拿 shell”。
3. **【高】授权判断散落在各处。** 设计里约定的 `can(principal, action, resource)` 没有落地。现在只有 admin、enrollment、runtime-install 这三处各自判断 role（`use-cases/admin.ts:44`、`enrollment.ts:165`、`runtime-install.ts:61`），其余路由默认全放行。
4. **【中】注册接口泄露邮箱是否已存在。** 返回 409「这个邮箱已经注册过了」（`accounts.ts:104`）。而且这个判断在 `openRegistration` 和名额检查**之前**，所以关闭注册后照样能枚举。登录和忘记密码已经做了防枚举，两边不一致。
5. **【中】没有防爆破的退避和锁定。** 登录限流的 key 是 IP+邮箱，换 IP 就能对同一个邮箱无限尝试。设计 §9 里的“每邮箱失败指数退避”和“每 IP 20 次/10 分钟”都没实现。
6. **【中】没有邀请，也不能删除用户。** 设计 §18 里说的“主人删掉”目前做不到，名额满了只能调大上限。
7. **【中】登录后不能改密码、改显示名、改邮箱，只能走“忘记密码”。**
8. **【低】审计没有记录登录成功/失败、注册、重置密码这类安全事件，也没有记来源 IP。** 资产审计依赖 WeakMap 兜底取操作者（`apps/server/src/assets.ts:76-82`），比较脆弱。
9. **【低】成员能读任意会话的资产清单（`assets.ts:85`），这和第 1 条是同一个根因。**
10. **【低】HUB_TOKEN 过渡期过了以后，Bearer 通道已经关掉（`main.ts:182`）。** 但没有个人 API token（设计 §7.2），脚本和 CLI 没有正式的认证方式。

## 二、业界常见做法（简要对比）
- **多租户和归属**：资源都带 `ownerId`/`createdBy`，最好再有 `workspaceId`。默认“只看自己的加上被共享的”，Owner/Admin 能看全部。
- **RBAC**：Owner / Admin / Member / Viewer 四档，用一个集中的策略函数 `can()` 加资源级 ACL（项目成员列表）。Worker 的使用权单独授权。
- **邀请制**：邀请链接或邮件指定角色，持邀请注册的人视为邮箱已验证，可以越过名额。开放注册默认关闭。
- **防爆破**：每账号失败退避，每 IP 再加总限流，可选 CAPTCHA，异常登录发邮件提醒。不永久锁号，避免被人恶意锁死。
- **账号生命周期**：自助改密码（要验证旧密码）、MFA/TOTP、软删除加匿名化、PAT（个人访问令牌）。

## 三、优化方案

| 优先级 | 事项 | 工作量 |
|---|---|---|
| **P0** | 删除项目改成仅 Owner 可做（或“Owner 加创建者”，需要先给 Project 加 `createdBy`，老数据归 Owner）。删除改成软删除，保留 N 天，可在后台恢复。 | 0.5–1 天 |
| **P0** | 成员默认不能在 `origin=local` 的 Worker 上开会话。可以加一个设置项 `membersCanUseLocalWorker`，默认关闭。 | 0.5 天 |
| **P0** | 注册防枚举：先检查开放注册和名额，再对“已存在”的邮箱返回和成功一样的响应（“请查收验证邮件”），同时给该邮箱发一封“有人试图用你的邮箱注册”的提醒。 | 0.5 天 |
| **P1** | 统一授权：在 domain 里写 `can(principal, action, resource)`，覆盖项目、会话、任务、资产、Worker，HTTP 层不再自己判断。加一套权限矩阵测试。 | 2–3 天 |
| **P1** | 资源归属：Project 和 Session 加 `createdBy`。成员可见范围做成可配置：全员可见（现状），或者仅自己加上被加入的项目。 | 2–3 天 |
| **P1** | 防爆破：按设计 §9 补上“每邮箱失败指数退避”和“每 IP 总量”限流。 | 0.5–1 天 |
| **P1** | 邀请：Owner 生成邀请链接或邮件并指定角色，可越过 `HUB_MAX_USERS`，邮箱视为已验证。开放注册默认改成关闭。 | 1.5–2 天 |
| **P1** | 删除用户（软删除并匿名化，资源转给 Owner），后台加按钮。 | 1 天 |
| **P2** | 个人设置：改密码（验证旧密码）、改显示名。 | 0.5–1 天 |
| **P2** | 审计扩展：登录成功/失败、注册、重置、踢设备，记录 IP。后台支持按人和动作筛选。 | 1 天 |
| **P2** | 增加 Admin 角色（能管理用户，不能改 hub 设置和机器），或 Viewer 只读角色。 | 1–2 天 |
| **P2** | 个人 API token（PAT）、TOTP 二次验证、新设备登录邮件提醒。 | 各 1–2 天 |

## 四、需要 David 决定的事
1. **成员的可见范围**：继续“全员看全部”（单团队模式），还是改成“只看自己的加上被共享的”？这个决定了 P1 归属模型的复杂度。
2. **删除项目的权限**：仅 Owner，还是 Owner 加创建者？要不要软删除和回收站？保留几天？
3. **成员能不能用“本机”Worker**：默认禁止，还是保持现状？
4. **注册策略**：开放注册是否改成默认关闭、改走邀请制？邀请是否可以越过 `HUB_MAX_USERS`？
5. **要不要加 Admin 或 Viewer 角色**，还是维持两档？
6. **删除用户时，他名下的项目和会话怎么处理**：转给 Owner，还是一起删？
