# Worktree 协作流程

本页约定如何开发 **agent-hub 仓库本身**，不涉及产品里的 WorkDir 或「创建 Worktree」功能。

## 1. 先定范围和工作位置

- **主会话留在 `agent-hub` 主检出**：盘点工作、分派子代理、审查差异、汇总验收并在获准后集成。需要在开发 worktree 验收时，给命令显式指定工作目录，不迁移主会话，也不把子代理的代码改到主检出。
- **子代理在指定 worktree 开发**：编辑、构建、聚焦测试都在该目录进行。功能开发、多文件修复、重构、实验和并行任务优先隔离。单文件小改或纯文档可以直接在主检出处理，但不得覆盖已有改动。
- 开工前检查 `git status --short` 和 `git worktree list`，确认基线提交、分支和已有改动。优先复用属于该任务且基线合适的 worktree；不能把别的任务未提交的改动当作新任务基线。
- 需要新建时，先说明任务、基线 SHA、分支和路径并获确认，再检查分支名无本地或远端冲突，且 `.slim/worktrees/` 已被 Git 忽略。默认分支为 `omos/<slug>`、目录为 `.slim/worktrees/<slug>/`；启用 `worktrees` 技能时同步维护本地登记 `.slim/worktrees.json`，不提交该文件。

## 2. 分派与开发

交接给子代理时至少写明：**worktree 绝对路径、基线 SHA、目标、允许修改的文件、聚焦检查和验证负责人**。子代理开工先核对目标路径与 Git 状态；如果工具默认从主检出解析相对路径，使用绝对路径编辑、为命令显式指定工作目录。

独立任务分别用自己的分支和 worktree。同一功能需要并行分工时，明确互不重叠的写入范围；相同文件如需多人修改，按依赖顺序交接。共享构建产物不要并发覆盖，E2E 使用独立端口和全新数据目录。子代理只跑约定的聚焦检查，回报改动路径、准确命令、退出码和证据位置；未获授权不提交、推送或部署。

## 3. 审查、验收与集成

1. **先收齐写入，再验收。** 主会话在所有写入者停手后，比对实际文件和基线差异，确认没混入其他任务、临时文件或凭据。发现问题由原负责人修复；修改后重跑受影响的检查。
2. **验证最终候选。** 非发布工作按范围验收；发布时以干净目录中的最终 Git 树跑 `npm ci`、`npm run ci` 和适用的 Playwright。Web 改动要按[测试与验收](testing/README.md)覆盖桌面和移动端。换基线或修改候选后，不沿用不匹配的结果。
3. **按授权集成。** 交代差异、验证结果、目标分支及尚未验证的边界，再执行获准的合并、变基或 cherry-pick。不要为了集成而切换、覆盖或清理含用户改动的主检出；必要时用获准的独立检出。提交、集成、推送、部署和清理分别以用户授权为准。
4. **部署后核对实际版本。** 按 [AGENTS.md 部署约定](../AGENTS.md#5-部署)记录候选 SHA、测试和部署证据；基础健康检查不等于真实业务冒烟。未经授权不操作生产账号或真实数据。

## 4. 交接与清理

交接写清：当前分支与 worktree 路径、基线和候选 SHA（未提交就注明）、未提交改动归属、测试与日志位置、是否已推送／部署、剩余工作或阻塞。主检出与其他 worktree 的改动原样保留。

确认任务已集成或妥善归档、worktree 无未提交改动，并得到明确授权后才移除 worktree 或删除分支。不能用 `git reset --hard`、`git clean`、强制移除或强推替代交接或处理冲突。
