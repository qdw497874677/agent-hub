# 2026-11-22 发布前代码与架构复审

范围：Hub HTTP/MCP 与权限、Worker 与运行时、SQLite 持久状态、Git 工作区与发布、Web 操作流程、部署可恢复性。静态发现与测试证据分开记录；本地端到端使用真实 Hub、Worker、Git 和 Chromium，模型由 ACP fixture 提供，不代表已验证生产模型或真实 GitHub 写入。

## 发布门禁

| 问题 | 影响 | 验证 |
| --- | --- | --- |
| 会话授权开关不能逐项撤销 | 用户以为缩小了权限，旧授权仍然生效 | 浏览器验证关闭其中一项和关闭最后一项，并读回服务端状态 |
| 发布确认没有绑定显示的提交 SHA | 工作树 HEAD 刷新后可能沿用用户对旧提交的确认 | 浏览器验证 SHA 变动须重新勾选；服务端仍独立核对当前 HEAD |
| Worker 连接令牌被运行时继承 | 子进程获得不属于它的连接凭据 | `apps/worker/src/credential-env.test.ts` 验证三种连接凭据保留给 Worker，但从继承环境移除；3 项通过 |
| 派工详情读取比确认权限更宽 | 其他项目成员能从详情读取指令和工作树位置，但不能确认该派工 | `apps/server/src/workspace-delegation.test.ts`：同项目创建者可读，非创建者与服务令牌不可读；14 项通过 |

## 架构判断与后续

- 项目能力以当前会话授权、发起身份和实时项目权限为边界；子会话不继承这些写权限。流程由提示词和资产编排，而不是在 Hub 固化开发、评审和回归顺序。
- 工作区调度、候选提交交接、发布是不同的写操作。发布需人确认精确 SHA；Worker 验证工作树、来源仓库及远端分支，GitHub PR 的 head 校验只代表核验当时，并非 GitHub 上永久不可变的承诺。
- Worker 断线不是回合结束。未知的 `sending` 继续占用会话是防止重放的有意设计；应补充可审计的人工恢复或同一回合的可信停止证明，不应恢复基于超时或断线的自动放行。
- 协调会话删除后的注册记录清理、派工 `preparing` 的崩溃恢复和候选导入的待确认回执，都需要明确对账或退役流程。不能把「重试」解释成自动再次执行可能已发生的外部写入。发布是否允许项目内有权限的另一位成员批准，需要单独明确；现有设计按项目推送权与 Worker 使用权授权，不应把它误写成仅发起人可发布。
- Worker 接入需要进一步区分遗留共享令牌与已注册机器能力：确认兼容面后收紧共享模式；旧的未绑定会话不宜仅凭 Worker 自报恢复归属。
- 先升级外置 Worker，再部署 Hub；校验上线机器与能力后再验会话。部署脚本仍可改进备用版本缺失时的回滚标记、包上传后校验，以及备份入口的显式契约。
- Web 剩余项：执行会话尚未创建时避免显示可点击入口；改善同名协调会话的区分、移动端长列表和状态播报。这些不应挡住本次核心修复的验证。
